# Gate 4: measured results

Generated by `bench/gate4.sh` (then `bench report`). Raw JSON for every row is in this directory. Configuration was fixed before measuring and is the same in every run. Sections 1, 2, 4 and 5 come from the first full run. The serving runs (section 3) were repeated after fixing two defects that the first run exposed, and both are reported: the load generator busy-waited and stole a CPU core from the system under test (those first results were discarded), and the cache path suffered a stampede (before/after table below). Hardware: see [`../ENVIRONMENT.md`](../ENVIRONMENT.md); all services share one 2-vCPU host, so these numbers are a floor, not a ceiling.

## 1. Ingest throughput (synthetic stream, event time advancing at wall-clock speed)

A run is **sustained** if total consumer lag did not grow: the least-squares slope of lag over the window is under 1% of the offered rate. With real-time pacing each zone's windows close once per event-time minute, so the Raft log carries only a few batches per minute regardless of event rate; this table measures the ingest path (Kafka, decoding, windowing). Freshness percentiles here come from few samples (one window close per partition per minute) and are bucket-resolution estimates.

## 2. Time-compressed replay of the real TLC month (commit-path stress)

Replaying March 2026 at a fixed rate compresses event time: the real stream averages about 1.47 trips/s, so 8,000 ev/s plays one event-time minute every ~11 ms: each partition closes a window roughly every 11 ms (about 90 per second) instead of once a minute, and every closed window produces a row per active zone, in the Raft log and in the Postgres history, so this stresses the commit path. The worker pipelines one proposal per partition and batches whatever closed meanwhile; when commits slow down, batches grow and freshness rises while ingest still keeps up.

### Cache stampede: before and after request coalescing

The first measured run showed the cached mode with a *worse* tail than linearizable reads: every hot key expired on the same 2 s TTL and workers invalidated zones in bursts, so concurrent misses hit the leader together. The fix was request coalescing for misses (one store read per missed zone set, shared by concurrent requests) and TTL jitter. Same rates, same deadline, same open-loop generator:

## 5. Write unavailability after a leader crash

`docker kill` (SIGKILL) of the leader under load, five separate runs. Unavailability = the longest stretch with no successful client write overlapping the 20 s after the kill. Election timeout is 300-600 ms (randomized); PreVote and the leader lease add a round trip.

Runs (ms): 360, 521, 381, 365, 514. Median **381 ms**, min 360 ms, max 521 ms.

Linearizability, partitions and the other fault scenarios: see [`../faults/SUMMARY.md`](../faults/SUMMARY.md).
